# 原始 source 与示例两表口径分析

这份记录只描述本次走查得到的事实和实现约束。`docs/specs/`、`contracts/v1/` 是当前工程合同；桌面上的两表是历史业务示例，示例中的客户、目标和人工补录值不能成为全局公式或默认值。

## 证据范围

- 原始目录：本机 source 数据目录，11 个 `.xlsx`，导出文件名时间均为 2026-09-30。
- 示例结果：本机示例结果目录中的核算表与推移表工作簿。
- 原始文件的业务覆盖最晚到 2026-09-30（销售出库最晚 2026-09-29；工资条含 2026-09；部分订单计划日期可到 2027-02）。示例两表列到 2026-10，示例的 2026-10 数值（销售 198,077.14、采购成本 98,103.72、人工 28,339、工时 720 等）不在本次 source 快照中，不能声称可由该快照重现。

## 可复算的指标口径

下列是从 source 事实推导出的候选规范观察，不是把示例企业写死在公式里。profile 应只负责把企业字段映射到这些稳定角色；公式和聚合由工作区指标定义执行。

1. **销售额（flow）**：`sales_delivery` 中状态为已确认的汇总行，按 `出库时间` 分桶，求 `出库产品售价总额(含税)/元` 之和。当前 source 计算出的 2025-07 至 2026-09 月值与示例推移表相符（例如 2026-09 为 780,141.98 元）；不能同时再加产品明细的 `产品售价合计(含税)/元`。
2. **销售成本（flow）**：同一批出库汇总行的 `出库产品成本总额/元`，按出库时间求和。毛利额为销售额减销售成本，毛利率为合并后的毛利额除销售额；不要平均行级毛利率。
3. **采购到货（flow）**：`purchase_receipt` 的确认汇总行按 `入库时间` 求 `入库产品采购价总额(含税)/元`。这是到货节奏/采购入库指标，不能直接替代已出库成本，也不能与采购订单金额重复计入成本。
4. **接单/采购签约（flow）**：分别取通过审批的订单汇总金额，按确认的订单期间字段聚合；计划送货/付款日期只作为计划，不冒充实绩。
5. **收款、付款、开票（flow）**：分别按收款时间、付款时间、开票时间聚合已确认金额。期间收付款差额不推出应收余额、现金余额或账龄。
6. **经营费用**：费用报销单的会计科目在嵌套列（当前导出可见 `税费`、`运费`、`办公用品`、`包装材料` 等）。profile 需要提供“原始科目 → 费用分类”的版本化映射；未映射科目保留 `待确认`，不能进入已分类合计。金额以已审核且支付确认的报销/票据口径为准，避免同一单据按票据明细和汇总重复求和。
7. **人工费**：以 `labor_payroll` 的 `当月实发` 作为候选现金人工支出；当前导出中 `当月工资薪金所得`、社保、公积金等字段大量为 0，不能据此判断真实为零。企业若选择“应计人工”或将社保、公积金纳入人工，必须在 profile/指标定义中明确，否则状态为 `configuration_required` 或 `待确认`。
8. **附加值与经营收益必须分开**：建议固定语义为“附加值（扣人工前） = 毛利额 − 已确认的非人工经营费用”；“经营收益（扣人工后） = 附加值 − 人工费”。两者均需保存公式、费用分类集合和证据；人工缺失时经营收益为 `待补`，不得把人工当 0。若工作区选择其他费用/人工处理方式，需通过版本化指标定义确认后重算。
9. **单位时间附加值**：附加值 ÷ 有效工时。当前 11 个 source 文件没有工时字段；工时必须由 `manual-input` 补录并带来源说明。无工时时显示 `待补`，不以 0 小时或默认出勤日推算。
10. **库存**：当前只有采购/销售明细中的可用库存数量和现金账户的初始金额，没有可审计的期初库存金额/完整库存流水。库存期初、期末金额和存货计价口径必须补录或由 profile 明确；现金账户不能映射成库存。
11. **目标/计划**：source 中未发现统一的月度目标、年度计划基线字段。示例核算表里的 40 万/月、360 万或 500 万是历史人工口径，不能作为默认目标。目标缺失时核算表/推移表显示 `待补/待确认`；补录后生成新 analysis revision。

## 缺失、冲突和 revision 处理建议

- 空白、`NA/N/A/-` 保留缺失标记；数字 0 才是有效零。目标、工时、费用分类、期初库存、人工口径任一关键输入缺失，相关指标和依赖指标均为 `pending_input`，不填 0。
- 需要区分“没有记录”（`missing`）、“有值但未确认映射”（`pending_input`）、“来源互相矛盾”（`conflict`）和“定义未配置”（`configuration_required`）。来源 profile、字段映射、费用分类和手工补录都应进入 revision 指纹。
- 重新扫描/补录不得覆盖旧 revision。界面先列受影响期间和差异摘要，用户主动执行“生成修订版”；旧两表继续可下载和审计。
- 扫描到 `核算表`、`推移表`、`差异分析` 或图表工作表时，直接返回 `generated_output_input_not_allowed`。示例结果只能作为展示/回归 golden，不进入 source observations。
- 本地 source→normalization→two_tables_v1 计算不调用大模型；诊断/任务生成是用户主动操作，且必须先确认当前 revision 的核算表和推移表都已物化。

## 对实现与测试的直接输入

- manufacturing profile 的首个真实夹具应覆盖上述 11 类来源的“汇总+明细”结构，至少断言销售 2026-09 = 780,141.98、成本 = 482,324.16，并断言费用/人工/目标/工时/库存未提供时保留待补。
- 另一个 profile（例如 service_demo）只需生成相同的规范观察和 `two_tables_v1` 列布局；两表 exporter 不应读取中文文件名、工作表名或企业客户名称。
- golden 测试应验证：只加汇总行不双计；缺人工时附加值可算而经营收益待补；缺工时时单位时间附加值待补；补录目标/工时/费用分类后 revision 递增且旧 revision 不变；把生成的两表重新扫描会被拒绝。
