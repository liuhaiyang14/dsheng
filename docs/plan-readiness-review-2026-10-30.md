# 整体计划复审与工程交接就绪度

日期：2026-10-30。审查基线：提交 `02fc2ff` 的实施计划、原型、内置提示词、5 份输出 Schema、版本清单及真实验收记录。

## 结论

**当前不能认定“执行此计划仅剩工程工作量”。** 本轮没有发现 P0；交叉去重后记录 10 组 P1 规格缺口、3 组 P2 补充项，另有独立的真实内容验收门禁未关闭。这里的 P1 指：缺少规则会使实现线程自行决定业务结果、数据保留、外发对象或模型交互行为；不等同于已实现软件出现了 10 个故障。

之前“已审范围内没有剩余 P0/P1”针对当时已发现缺陷的修复及特定返回样例，不能推广为整个产品合同已经闭合。本次横向检查数据、历史、任务、Provider、上下文和发布之间的衔接，发现了新的规格问题。

本报告的推荐方案是**供当前规划主 Agent 收口的具体建议，尚未替代实施计划和提示词合同**。实现线程不得在多个建议中自行选择。此轮未修改提示词、未改变既有验收结果、未调用 Provider，剩余调用授权仍为 0。当前处于计划阶段，未开始产品实现。

## 1. 审查方式与责任

主 Agent 汇总三条独立只读审查：

- 数据审查：指标口径、源数据归并、日历/比较、SQLite、分析重做与历史。
- 提示词审查：任务与三框架、请求合同、多轮上下文、警告、实际内容覆盖。
- 交付审查：任务编辑/推进、GUI/CLI、Provider 选择、数据升级与四类交付物。

审查结论依据仓库规范，必要时仅在本机核对用户提供的 Skill 方法条款；没有复制真实企业资料进入本文件。所有来源行号以审查基线为准；后续修改后优先按节名、字段和 issue ID 定位。

## 2. P1：需要在规划阶段关闭的规格缺口

### PR-01 指标计算、聚合与重复来源归并

依据：主计划 §6.2–6.4、§7 的 metric_definitions，基线第 179、198–211、270–274 行。

风险：核算文件里的推移表与独立推移文件同时导入，或明细和汇总同时存在，可能重复计算；结存数量缺少期初/累计起点；季度利润率、单位时间附加值可能被错误求和或平均。仅写“由企业配置 formula_json/aggregation”仍要求实现者设计其业务含义。

推荐收口：

- 给出指标注册表：稳定 metric key、流量/时点/比例类型、单位/币种/含税口径、方向、必要输入、允许公式与聚合方式。企业特定参数作为运行时配置，缺配置时明确阻断对应指标。
- 流量按非重叠可比明细求和；时点指标取可证明的期末余额；比例按汇总分子/分母重算，未知聚合方式不得自行推断。
- 库存必须有期初余额或可验证的完整累计起点，不把缺期初当零。
- 同一指标/期间/范围的重复汇总只计一次；明细与汇总不相加。来源冲突同时保留，必须经用户选择主来源或补充说明，不能静默选值。
- 固定小数精度、展示舍入与中间计算、零/负分母、退货/冲销的规则，不让 UI 和 CLI 各自解释。

关闭证据：版本化指标/来源规则表及合成算例，至少覆盖重复推移、明细+汇总、缺期初、比例跨期汇总、冲突与负/零分母。需要业务规则定稿；无需模型研究公式。

### PR-02 日历、周期切换与同比环比边界

依据：主计划 §6.5，基线第 221–225 行；验收 22、25–29。

风险：“上一年同期”“明确兼容”没有算法定义；周同比可能前 52 周或上一年同周，闰日、53 周、财季、半月变更策略、自定义范围跨闰年都会产生不同结果。

推荐收口：固定 day/week/month/fiscal-quarter/custom 对照表，明确起止日期是否闭区间、周规则与闰年处理；不存在的对应日期直接标不可比，不默默截短。跨策略比较基于日历/指标/范围兼容签名，不只比较版本号。月度汇总不能拆日；完整日度可否聚合为月度以及覆盖检查必须明定。跨策略生效日的范围要求显式选策略，禁止自动混算。负基期变化率应有明确指标政策；缺政策只显示绝对变化与原因。

关闭证据：可独立复算的边界日期表与兼容矩阵。具体周同比默认仍须由规划主 Agent 写定，而非交给开发者选择；无需真实模型。

### PR-03 分析 revision、异步生成和引用快照

依据：主计划 §7、§8.2–8.3，基线第 287–340、399、409、457 行。

风险：重做期间保持 run_id，却改变指标、手工输入或公式；旧诊断仍符合“同 run 可引用”。只核文件 hash 无法发现手工目标变化；请求等待期间重做分析，也可能把旧依据的结果写为最新结果。比较基期重做后，旧导出可能跟着漂移。

推荐收口：session/report/生成结果绑定 analysis_revision_no 与输入指纹，指纹覆盖源/选定范围、映射、指标版本、手工输入、比较基期快照和目标期间。诊断引用同时固定 report_revision_no。比较保留 base_run_id+base_revision_no。旧报告可读且显示过期，默认不进入当前引用；失效引用在本地提示重选并重新确认，不偷偷切换、也不让模型猜过期。提交前重新检查 revision，冲突则保留旧记录并拒绝提交为当前结果。

关闭证据：完整绑定字段与事务规则；覆盖仅改手工输入、请求中重做、旧报告引用、基期重做与历史导出。属于确定性生命周期规则；修改任务引用 payload 后需要相应真实内容回归。

### PR-04 任务/步骤永久身份、跨期延续与重生成合并

依据：主计划 §7、§9.4，基线第 315–322、340、538–542 行；任务 payload 第 385–402 行；task-output.schema.json 的 task_key/step_id。

风险：模型返回任意非空 key，输入没有已有任务身份；再次生成换标题或 key，就可能新建重复任务、误把旧任务标替代。单个 run 内的 task_key 和单个 cycle_role 也不足以表达同一行动先作下期计划、再作后期检视。

推荐轻量方案（不增加模型匹配）：

- 模型 task_key/step_id 只作单次候选局部键；应用分配永久 task/step UUID，分别校验本次候选键唯一。
- 重生成先保存候选快照和差异；用户明确选新建、映射到已有任务/步骤或替代，并确认字段变更后事务应用。未映射旧任务保持原状，不能自动覆盖、删除或标替代。CLI 提供同样的 reconcile 合同。
- 人工内容、删除意图、责任人、完成状态与事件保留；模型生成 completed 不能完成本地任务。新建步骤初始为 not_started，映射旧步骤保持实际状态。
- 跨期视图通过 task-period 关联引用同一任务，不复制另一份进度历史；对旧期间导出的任务版本及事件截止时间另给明确规则。

关闭证据：应用 ID/候选 ID、用户确认 diff、字段覆盖优先级、跨期关联和 CLI 合同，以及纯本地合并测试。该方案不必让模型学会稳定匹配，避免新增不必要的提示词调试。

### PR-05 任务字段保存、人工编辑及进度状态不闭合

依据：主计划 §5.2、§7、§8.2、§9.4，基线第 145–146、314–322、411、528–536 行。

风险：输出含 start_date/done_criteria/evidence_ids/status，task_steps 表只有 due_date/checked；资源、验收标准、SMART、needs_review 未明确如何成为可编辑的当前态。0%不能完成并未明确 50%能否完成；手工覆盖遇步骤变化、阻塞优先级、重开后的 completed_at 都未定。

推荐收口：

- 建立“输出字段→当前态→不可变生成快照→UI/CLI patch→导出”映射；可以使用版本化 JSON，但明确唯一读写来源。checked 与 status 不作为两个独立真值。
- 人工改目标/步骤后，旧 SMART 评价保留为生成时快照并标需要复核，不再次自动调用模型、不冒充最新评价。
- 固定状态转换表：完成要求100%、待开始要求0%、阻塞必须原因；明确自动进度与手工覆盖的持久模式及下一次步骤变化行为。延期建议作为由截止日期/未完成推导的标记，避免与阻塞互斥。
- 重开清除当前 completed_at，旧完成事件保留；所有字段/步骤修改按相同事务与事件规则执行。

关闭证据：字段映射、patch schema、状态表与边界测试，原型按最终表调整。属于本地产品规则，无需模型决定任务实际进度。

### PR-06 多 Provider 路由及发送确认绑定

依据：主计划 §5.1、§7、§8，基线第 108–112、133–134、247–248 行。

风险：可保存多条 Provider，但没有默认或显式选择规则；预览后另一客户端改地址，原确认可能被用于另一接收方。

推荐收口：UI/CLI 显式 provider_id 优先；省略时只能使用工作区已确认的 active_provider_id，否则本地拒绝。Provider 配置 revision 与本次路由/模型纳入预览和 attempt 快照；配置变化使旧确认失效。禁止自动 fallback、取第一条或最近一条。凭据变更用本地 revision 标识，不把密钥或可逆凭据内容写进 manifest/日志。

关闭证据：字段/命令/确认快照合同和配置竞争测试。无需额外模型决策。

### PR-07 删除、共享数据库升级与恢复边界

依据：主计划 §5.2、§9.4、§10.2–11，基线第 158、538、570–594 行。

风险有两项，须分别关闭：

1. 删除历史只写“二次确认”，未定义跨期任务、诊断/turn、revision、比较引用和导出快照是否删除。建议保留已承诺的删除动作，但有活动请求或跨期间存活依赖时阻止物理删除并列依赖；无依赖时预览 run-local 影响清单并事务删除。不得默默把删除改成归档，也不得级联删仍在推进的任务。
2. 独立 CLI 与桌面升级不同步时可能写入不支持的数据库。建议明确 schema 兼容范围、旧客户端拒绝不兼容库、迁移独占锁、活动实例退出、迁移前本地一致性备份、失败保留原库、禁止自动降级；卸载/重装默认保留用户数据。备份含明文 Key，属于受控本地数据，不进入业务导出和发布包。

关闭证据：删除依赖矩阵、迁移/版本规则及两组本地事务用例。无需模型调试，不能只靠一次确认代替影响定义。

### PR-08 月度目标下限缺少指标方向限制

依据：task/system.md 第 13 行；主计划 §8.2 第 420 行、验收 49。

风险：“月度预定不低于年度月度分解或去年同期”可被解释为适用所有指标，包括费用/耗时。现有费用样例有冲突并返回 null，没有验证无冲突的成本目标。用户 Skill 本身存在泛化措辞，不能靠工程实现猜测，更不能直接把费用改成 min。

推荐收口：指标合同明确 direction 与 target_constraint_scope；收入/增长类采用何种下限、费用/时间类仅采用显式预算或已确认改善目标、未知方向如何处理，都在规划阶段定稿。没有减费/缩时幅度依据不生成数字。将规则同步到任务 system、payload 与验收，不通过向测试 payload 偷塞规则弥补提示词缺失。

关闭证据：定稿规则、prompt 升版及真实无冲突收入/费用/耗时样例，附非月度回归。这一项需要提示词工作和真实内容验收，不能算纯编码。

### PR-09 多轮上下文、澄清承接与更正旧事实

依据：主计划 §8.3 的第 455–478 行；diagnosis system/user；报告 facts 与 questions 合同。

风险：必要证据、最近相关摘要和有效新内容仍是自然语言要求。needs_clarification 不更新报告，而下一轮开放问题仅从报告恢复；用户只答“是”时，可能丢掉待澄清问题及被搁置原文。用户更正先前说法后，旧 accepted facts 是否再次发出也没有明确当前态。

推荐收口：

- 冻结 context_policy 的纳入集合、排序、重复消除、预算、原文长度规则和溢出行为。摘要由确定性投影生成，不增加后台 LLM 摘要调用，不让实现者发明语义相关度算法。
- 将 pending clarification 的 turn ID、原话、具体问题和回答关联单独定义；轻量可要求用户在本地补充表单完整重述待采纳事实。孤立“是/不是”不让模型猜原意，先给本地补全提示，且不计请求。
- 旧事实更正必须确定处理方式：例如一期发现对既有事实的显式更正时冻结旧会话、另建并重新确认；或定义 superseded/retracted 及依赖失效。两者不可留给实现线程自由选择。
- 原始记录缺失且要求书面依据的 warning，在来源锁定下可以合法地保持 active；新增来源应新建报告。正向解除只测试已有来源和足够补充确能解除的真实风险，不用普通未答问题/轮次进度凑 warning。

关闭证据：字段级 context 合同、澄清恢复/更正规则、警告证据类型矩阵；如改变模型可见上下文或公共提示词，必须真实多轮验证并回归跑题。

### PR-10 单次请求与分块行为冲突

依据：主计划 §5.2、§8，基线第 143、348、409、495、685 行；验收 7。

风险：一边规定每次操作最多一个请求，一边允许确定性分块，缺跨块证据、任务去重、合并、失败和费用确认规则。模型输入限制与响应大小也未有一致的执行合同。

推荐轻量方案：首版一次操作只发一次请求，超限在本地停止并要求缩范围、重新预览确认；诊断如改变已锁范围则新建报告。明确不做多次模型请求分块/归并。固定用户可配的模型上下文预算、保守估算方法、应用硬上限和响应大小上限，实际超限失败保护旧结果。

关闭证据：统一删除模棱两可的分块分支，补预算/上限表和边界用例；无需引入分块汇总提示词。

## 5. 什么可以留给实现线程

以下属于正常工程工作：Rust 类型与模块、migration SQL、锁与事务实现、文件解析器、确定性公式引擎、React/ECharts、Tauri IPC、CLI参数解析、构建打包、自动化测试、脱敏日志、性能与兼容性验证。它们只要遵循闭合合同，不需要当前阶段写出全部代码。

以下属于产品运行时输入，不是未做完的研发决策：企业时区/财年/周起始日、企业核算口径、字段映射、手工补录、负责人/期限、Provider 配置及每次外发确认。前提是选项、默认值、校验和数据影响在规格中已经明确。

以下不能下放：指标业务含义、目标方向规则、任务身份/合并、来源/版本变化语义、多轮上下文采纳规则、提示词研究/润色及内容冻结。它们由当前规划主 Agent 收口，必要业务选择再集中向用户确认。

## 6. 最短收口顺序与完成证据

1. 当前规划主 Agent 先定稿 PR-01–10 的确定性业务/产品规则，并补 PR-11–13 交接附件；每项给出唯一执行规则，不留“方案A或B由实现选择”。
2. 同步主计划、输入/输出合同、SQLite字段映射、UI/CLI动作和新增验收，保留现有1–64编号，后续追加编号；纯本地验证不调用模型。
3. 只对确有语义或上下文变化的 prompt 升版，按影响范围执行 LV-01–08 的真实内容检查；失败按实记录并在当前规划阶段修订。
4. 三方向独立复审：无未关闭P0/P1、没有方法论待定项、受影响真实内容有证据、资源版本/哈希一致，才声明“工程可开工”。
5. 形成冻结清单：指标/比较规格、源/模板映射、任务合并/状态、版本与数据生命周期、Provider路由/预算、context策略、提示词及验收矩阵、工作包所有权。然后实现线程仅编码、集成和工程验证。

不报一个掩盖门禁的“完成百分比”：现有64项是产品验收用例，不能因文档写完就计为实现通过。当前的明确判断为 **engineering_ready=false**。即使规划全部冻结，也只能合理承诺“不主动把业务和提示词设计下放实现线程”，不能保证任意Provider或模型升级后永远不暴露新的行为问题；此类偏差应按变更流程回到规划负责人，不由实现Agent临时改规则。
